# GifCut v0.3.79 — Multimedia Editing Workspace Design

**Status:** Draft for approval  
**Repository:** `G3fic/G3fiCut`  
**Base:** `main` at `72cf1c6479a14830766fb4ddf2c556f29ab7f041` (`v0.3.78`)  
**Target application version:** `0.3.79+87`  
**Target visible name:** `GifCut v0.3.79`

## Intent

Turn the current single-source video editor into a practical multi-media desktop editor while matching the supplied CapCut references. The person editing should be able to import or drop video, photo and audio files into one media library, add text, place independent items on timeline tracks, select effects/transitions in a visual tile library, edit the selected item's properties in a right-hand inspector, and export the same composition they saw in preview.

The screenshots are layout references, not a request to copy CapCut branding. Preserve GifCut's identity and local-first workflow.

## Current state and constraints

- The application is Flutter desktop and Windows-first. FFmpeg handles export; `media_kit`/`media_kit_video` handles playback.
- `pubspec.yaml` is currently `0.3.78+86`.
- `ProjectDocument` schema v3 stores one `videoPath`, a list of source ranges from that video, one extracted audio file, effect blocks and transitions. Photo overlays are runtime UI state rather than first-class persisted media.
- `main.dart` contains most UI, player, timeline and export behavior. Existing support must be extracted carefully into focused files rather than rewritten blindly.
- The preview always paints a blurred duplicate of the source video behind the fitted video. That must no longer be the default.
- The timeline currently reserves a 112 px leading label gutter. The requested composition should start its time ruler and clip content at the left edge; track labels can be compact overlays / headers rather than a permanent empty gutter.
- Existing projects must continue opening. New project schema work must preserve schema v1-v3 compatibility through migration.

## Goals

1. Adopt the supplied editor layout: compact top category tabs over the left library, a central preview, a right inspector, and a full-width bottom timeline.
2. The left library accepts multiple video, image and audio files both through the file picker and by dragging from Windows File Explorer.
3. Add text/title clips and place video, image, audio and text items on independent timeline tracks.
4. Persist all imported assets, timeline items, transforms, clip ranges, text properties, effect blocks, transitions and canvas background settings.
5. Preview and export must use the same composition order and the same enabled effects/transitions.
6. Render effects and transitions in a grid of named square/portrait cards with a real image preview that animates the selected filter / xfade style. Clicking a card selects it and opens its controls in the right inspector; it must not silently insert an effect.
7. The canvas is solid black by default. A blurred-video background becomes a separate, explicit, reversible canvas-background option.
8. Update the application version and visible title to `GifCut v0.3.79`.

## Non-goals for this release

- AI-generated footage, automated subtitles/transcription, online asset catalogues, cloud media storage or account-based services.
- A full keyframe/curve editor or 3D compositing system.
- Replacing Flutter, FFmpeg or `media_kit` with a browser-based editor.
- Claiming every FFmpeg filter is guaranteed to preview identically in real time. Every shipped preset must have a working preview representation and a verified export mapping.
- Releasing a signed installer until CI has built and tested the new version.

## Approaches considered

### A. Re-skin the existing editor

Move panels, add cards and keep the one-video data model. This is the smallest change, but separate videos/audio/text would remain superficial and could not be represented or exported reliably. Rejected because it does not satisfy variant B.

### B. Extend GifCut's project and render model (chosen)

Keep Flutter, `media_kit`, FFmpeg and existing editing features. Introduce a backwards-compatible media-asset / track-item model, make photo/text/audio/video first-class timeline items, then build the reference layout and effect library on those stable interfaces. This costs more implementation and migration work, but makes the visible controls correspond to real project data and export behavior.

### C. Embed an external editor engine or web editor

This would introduce another rendering/runtime stack and complicate local-file access, Windows packaging, updater and project compatibility. It is not justified for the current desktop application and is rejected.

## Architecture

The work is split into three cooperating sub-projects, with interfaces fixed before implementation:

1. **Editor workspace and media intake** — the visible layout, category tabs, import, native drag-and-drop and media-library state.
2. **Multi-media project, timeline and compositor** — schema v4, migration, independent tracks, text/image/video/audio clips, preview composition and FFmpeg export.
3. **Effects and transitions library** — card catalogue, animated image demonstrations, selection semantics, right-inspector controls and real timeline/export application.

The canonical project model is the source of truth. Widgets do not own duplicate clip state. Media assets have stable IDs and file paths; timeline items reference those IDs and carry source range, sequence start, duration, transform, opacity, volume and track order as applicable. Separate track/item types can share a common serializable base only where their behavior is genuinely common.

The compositor is responsible for resolving active items at a sequence time and drawing them in a deterministic order. Export consumes that same resolved sequence and builds FFmpeg inputs/filter graphs. Text is rendered from saved text/style data to transparent raster overlays for export, avoiding shell-string injection and dependence on the host's arbitrary font names. Audio tracks are mixed intentionally, with source-audio behavior explicit in project/export settings.

## Workspace requirements

- Left library starts with Media, Audio, Text, Stickers, Effects, Transitions, Captions and Filters tabs, matching the reference's compact icon-and-label navigation. Keep the library itself inside the left dock; do not keep a second permanent vertical tool rail.
- Media view shows imported assets as cards/rows with type icon, thumbnail/waveform, filename and duration. Import accepts multiple files. Unsupported file types are reported without discarding valid files from the same drop.
- External file drag-and-drop supports multiple files from Explorer. Drop into the media library imports assets. Dragging a library item to a compatible timeline track creates a timeline item.
- Text view provides “Add text” and a small set of useful built-in title styles. Selecting a text clip opens text content, font, size, color, alignment, opacity, position and duration in the inspector.
- The center preview preserves the project aspect ratio with black surround. The optional blurred background is an explicit canvas setting, separate from the clip's “Размытие” effect.
- Right inspector stays docked at the far right and shows properties for the selected video, image, audio, text, effect or transition. Use compact property tabs as in the reference (Video, Audio, Speed, Animation, Adjust, AI stylize where relevant); hide irrelevant tabs for a selected object rather than showing inert controls.
- Timeline spans the full window width. The first ruler tick and clip area align to x=0; track names are compact overlays/header controls and must not create a 112 px empty offset. Video, image, text, audio, effect and transition rows appear only when needed. Keep resize handles, zoom, snapping, playhead, selection and undo/redo.
- Panel resizing remains supported. Minimum panel widths must prevent the preview/inspector from collapsing.

## Media / timeline requirements

- Support multiple video assets and clips that can reference different sources in one sequence. Each clip keeps its asset ID, source in/out, sequence start and duration.
- Support multiple still-image clips with sequence timing, transform, opacity and ordering. Existing photo-overlay behavior becomes a first-class persisted image clip.
- Support multiple audio assets and clips, independent trim/sequence position, gain and optional fade; preview audio monitoring and export mixing must not silently duplicate source audio.
- Support text/title clips with saved content and style.
- Keep effects as timeline-scoped blocks and transitions attached to adjacent video clip joins. Selecting a card and selecting an already placed timeline block are distinct states.
- Use stable IDs for assets, tracks and timeline items. Project schema v4 must migrate legacy single-video v1-v3 documents without losing ranges, effect/transition blocks, extracted audio or project settings.
- When a media file is unavailable, preserve the item and show a relink/missing-file state instead of silently dropping it.

## Effects / transitions requirements

- Replace the simplified moving-rectangle hover preview with real sample imagery. Prefer a frame thumbnail extracted from an imported project asset; when no asset is loaded, use bundled, locally available sample artwork.
- Cards are equal-sized, named and organized by category/subcategory. A card preview demonstrates the actual color/filter transform or the actual transition motion, not just a generic icon animation.
- Hover/focus or selection plays a short, muted, looping demonstration. Stop offscreen/unselected animations to avoid excessive CPU/GPU use.
- A click selects the card and updates the right inspector. Inspector shows the description, relevant controls and an explicit “Добавить на таймлайн” / “Применить” action.
- Effect parameters and transition duration/type are persisted and validated. Export uses the exact FFmpeg filter/xfade mapping for the selected preset. Unsupported FFmpeg build filters must be caught in tests or surfaced as a clear export error, not silently ignored.
- Effects and transitions must be usable even before a clip is selected where the action is meaningful; insertion into the timeline must give clear feedback when no suitable video clip/join exists.

## Background behavior

- Default: black surround inside the project canvas; no duplicate blurred video layer.
- Provide a named “Фон предпросмотра” setting with at least “Чёрный” and “Размытие исходного видео” modes.
- Toggling the mode affects only canvas background and does not modify the source clip's visual effect.
- Persist the choice and apply the same composition in export. A project opened from v1-v3 defaults to black (the old automatic blur is intentionally not migrated as enabled state).

## Version / release requirements

- Set `pubspec.yaml` to `version: 0.3.79+87`.
- Set the fallback `appVersion` to `0.3.79` and the app/window-visible title to `GifCut v0.3.79`.
- Add a `GifCut v0.3.79 — 2026-11-01` changelog entry and update README feature statements / roadmap so they describe implemented behavior, not planned behavior.
- Keep installer/release naming consistent with `GifCut-Setup-0.3.79.exe` where configured. Publish a GitHub Release only after Actions produces a successful Windows installer and all checks pass.

## Test and acceptance criteria

- Unit tests cover schema v1-v3 migration to v4, stable IDs, validation, missing media paths, multiple source videos, image/text/audio clips, track ordering and undo/redo.
- Widget tests cover the left category tabs, media cards, file import actions, right inspector selection, background mode toggle, no blurred background by default, and zero-width timeline label gutter.
- Drag-and-drop tests exercise multiple files, mixed supported/unsupported inputs, duplicate paths and rejected file types. A Windows manual acceptance test confirms files can be dropped from File Explorer.
- Export integration tests create short local sample clips and verify the output contains the expected video composition, timing, text/image overlay, transitions and audio mix. Test FFmpeg failures and cleanup paths.
- Effect catalogue tests assert every visible preset has a preview renderer and an export mapping; transition tests verify xfade mode, duration and valid join association.
- CI runs format, analyzer and the full Flutter test suite; Windows workflow builds the app and installer. No release is published based solely on static review.

## Builder decisions

The implementation owner may choose exact widget decomposition, thumbnail caching, sample-art source and FFmpeg intermediate formats, provided the acceptance criteria hold. Keep file paths local; do not upload media. Keep the stable package version unless CI reveals an incompatibility, in which case record the compatible pin and reason.
